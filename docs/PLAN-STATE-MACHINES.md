# State machines in Tell-Tail

This plan covers the production code in checkout `c512ada`, including features under development. The inventory follows events that change how Tell-Tail handles the *next* event. It covers the Rust library and binary, helper processes, embedded dashboard, and the boundaries between them. Release and validation tooling have their own lifecycles, listed at the end.

**Start with the dashboard’s manual retry behavior.** Three different recovery conditions promise the same user action. One browser event bypasses that promise. Fixing it gives users predictable recovery, gives maintainers one place to change the rule, and gives coding agents an executable example of when to open a connection. Use small, local transition functions or Rust types where there is a comparable payoff. The existing public input state already has the right vocabulary.

## First change

The dashboard guide says a full server, an invalid frame, and a publisher failure each require **Retry connection**. The visibility handler enforces that rule. The persisted `pageshow` handler calls `connect()` directly. In a Chromium probe against the embedded dashboard, entering each of those three states and dispatching a persisted `pagehide` / `pageshow` pair increased the number of EventSource instances from one to two without a click. The probe supplied the lifecycle events and a test EventSource. A separate Back navigation in the same environment performed a fresh load. The observed discrepancy concerns restoration of an existing page instance. [Dashboard implementation](../web/dashboard.mjs) · [Dashboard guide](WEB-DASHBOARD.md#connection-behavior)

| Prior condition | Event | Expected observable result |
| --- | --- | --- |
| Capacity, invalid frame, or publisher failure | Tab shown or cached page restored | Retain the reason, last good values, and Retry button. Open zero streams and schedule zero retries. |
| Same three conditions, page visible | User chooses Retry | Start exactly one connection attempt. Keep the displayed metrics until a newer valid frame arrives. |
| Live page, including a frozen display | Hide and show, or leave and restore | Retire the old connection and pending recovery work. Reconnect once when visible. A frozen display keeps its values. |
| Recovery request outstanding | Late reply from a retired attempt | Ignore the reply, including its capacity header. The current attempt owns the banner and timers. |
| Frozen with a final input frame available | Restore, then resume display | Keep the connection closed. Announce finality and show the final metrics when the user resumes. |

Extend the existing browser recovery tests with these event sequences. Exercise visible restoration and both orders of visibility and page restoration. First confirm the three manual-retry cases fail against the current code. Then give automatic connection attempts one eligibility check shared by the existing callbacks. Keep the explicit Retry action distinct. Preserve the one-active-stream bound, current backoff, warning deduplication, keyboard behavior, and accessible status text. Ship the regression test and fix in one commit. [Live browser tests](../browser-tests/live.test.mjs) · [Visibility test](../browser-tests/visibility.test.mjs)

## Implementation order and acceptance

1. **Ship the browser retry fix and its regression cases.** Count connection attempts and assert the visible banner and retained values. Use the exact event sequence as the test name or test data so an agent can find the owning rule by searching for the symptom.
2. **Protect file handoff before changing its representation.** Run the follower and live rotation tests. Add the smallest missing sequence that crosses path disappearance, descriptor drain, and a partial record. Assert ordered records, skipped and pending bytes, and the boundary count at the appropriate layer. If a local type would eliminate an impossible combination, move the descriptor, offset, and replacement into that type in a separate verified commit. Include a paired throughput check for any read-path change.
3. **Isolate server shutdown decisions when working on the serving loop.** Use the existing integration tests to distinguish normal EOF, input failure, publisher failure, and signal during final delivery. Add a case only for a missing observable outcome. Make one local change at a time, starting with the normal-EOF retention decision or the drain deadline. Verify received event kind, final values, new connection admission, and process exit.
4. **Keep the remaining machines at their current level of detail until a specific transition needs work.** For each proposed change, identify the user-visible outcome, the one module that decides it, and a deterministic event sequence another contributor or agent can run. If the existing code and test already answer all three, the inventory completes that item.

For each implementation increment, run the focused tests before and after, then commit the change with its regression coverage. Keep each increment independently revertible. Preserve CLI JSON schema 2, web frames schema 1 including older frames with absent optional fields, Prometheus series, exit semantics, and public library entry points. Use reviewed fixtures as compatibility baselines. For a Rust change, use the existing default, CLI-only, and snapshot-notifications test configurations. For a dashboard change, rebuild the binary to embed the edited assets and run the browser suite, including the headed visibility check. For a hot-path or resource-ownership change, use the relevant existing throughput, freshness, backpressure, or teardown check. [Compatibility tests](../tests/compatibility.rs) · [Web frame fixtures and tests](../tests/web_frame.rs) · [Existing checks](../.github/workflows/ci.yml)
